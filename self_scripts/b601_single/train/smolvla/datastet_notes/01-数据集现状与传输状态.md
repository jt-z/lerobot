## 传输是否完成的判断方法

从**接收端**只能证明「已到的这批是完好的」，无法证明「源端不再发了」。判断依据分三层：

### 1. 有没有传输进程在跑（弱证据）

```bash
ps aux | grep -Ei 'rsync|scp|sftp|rclone' | grep -v grep
```

实测：无任何传输进程。但源端可能是**按需手动推送**，本方法只能说明「此刻没有」。

### 2. 有没有半成品残留（强证据）

```bash
find $ROOT -name '*.partial' -o -name '*.tmp' -o -name '*.crdownload'
```

实测：无。`tmp*/` 目录是 9-16 17:27 的**源端录制残留**（内含 `observation.images.*_161.mp4`），
与传输无关，README 已记载其不影响训练。

### 3. 视频/数据与 meta 是否自洽（最强证据，推荐）

传输中断会在**尾部**留下截断。用 meta 里的 `to_timestamp` 逐集核对视频时长：

| 检查 | 实测结果 |
|---|---|
| 视频文件缺失 | **0** |
| 视频被截断（时长 < `to_timestamp`） | **0**（余量精确 +0.00s） |
| 数据 parquet 总行数 == meta `total_frames` | 修复后 **533,168 == 533,168** ✅ |

末集 ep222 的三路视频逐一核对：

| 相机 | 文件 | 文件时长 | meta `to_timestamp` | 余量 |
|---|---|---|---|---|
| hand | `file-020.mp4` | 1345.87s | 1345.87s | +0.00s |
| front | `file-028.mp4` | 453.67s | 453.67s | +0.00s |
| top | `file-029.mp4` | 505.10s | 505.10s | +0.00s |

**结论**：已到的数据（含 9-18 两批）**视频侧完整无截断**。
但源端是否还会发更多，本机判断不了——9-18 两批间隔 28 分钟，9-16 那天的间隔是十几分钟到一小时，都不规则。
