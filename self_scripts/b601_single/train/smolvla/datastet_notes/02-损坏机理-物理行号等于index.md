# 02-损坏机理：为什么「物理行号 == index」是硬约束

## 损坏是什么

`data/chunk-000/file-009.parquet` 末尾多出一个 **11,005 行**的废弃 row group。

```
row groups = [2034, 2180, 2925, 2458, 2679, 2447, 2481, 2142, 2247, 2230, 11005]
                                                              ↑ 正常内容（eps 151–160, 23,823 行）
                                                                      ↑ 废弃块 11,005 行
```

废弃块的属性：

| 属性 | 值 |
|---|---|
| 行数 | 11,005 |
| `episode_index` | 全部标成 **161** |
| `index` 区间 | 418,360 .. 429,364 |
| `timestamp` 区间 | 0 .. 366.8s（11,005 ÷ 30fps = 366.8s，自洽） |
| 来源 | ep161 **第一遍录制崩掉**时泄漏的 writer 缓冲；该集随后被重录 |

对照：**真正的 ep161 只有 2,110 帧（70.3s）**，它的数据在 `file-010.parquet` 里。

所以「ep161」这个名字下有两份内容：

| 位置 | 行数 | 时长 | 性质 |
|---|---|---|---|
| `file-009` 末尾 | 11,005 | 366.8s | 废弃（录崩的那一遍） |
| `file-010` 开头 | 2,110 | 70.3s | 真身（重录的那一遍） |

## 为什么会破坏训练

`LeRobotDataset` 读取数据的位置由 `meta/episodes` 里的 `dataset_from_index` /
`dataset_to_index` 决定，而底层 HF datasets 是把 `data/chunk-000/*.parquet`
**按文件名顺序做位置拼接**的。于是有一个硬约束：

```
meta 里的 dataset_from_index  ==  该集第一帧在拼接结果里的物理行号
```

也就是说 **`index` 列的值必须等于它所在的行号**。

废弃块破坏了这个等式（它把后面所有内容整体后移 11,005 行）：

| 文件 | 物理起始行 | `index` 最小值 | 一致 |
|---|---|---|---|
| `file-000` .. `file-009` | 0 .. 394,537 | 同 | ✅ |
| `file-010` | 429,365 | **418,360** | ❌ 差 11,005 |
| `file-011` | 438,197 | 427,192 | ❌ |
| `file-012` | 462,628 | 451,623 | ❌ |
| `file-013` | 464,144 | 453,139 | ❌ |
| `file-014` | 503,797 | 492,792 | ❌ |

后果：`ds[418360]` 之后的取帧**按位置偏移读到了别的 episode 的行**，
而视频仍然按 meta 里的 `episode_index` + `timestamp` 去查对应 mp4
→ **state/action 与图像来自不同的时刻，图文错配**。

### 影响面

| 项 | 数值 |
|---|---|
| meta `total_frames` | 533,168 |
| parquet 实际行数 | 544,173 |
| 差值 | **11,005** |
| 首个错配位置 | `index` 420,470（ep162 起始） |
| 受影响帧数 | 533,168 − 420,470 = **112,698** |
| 占比 | **≈ 21%** |

即 **ep162 及之后的所有 episode 都错**。

## 为什么「9-16 会崩、9-18 不崩」

两次的**损坏内容完全相同**（sha256 逐字节一致），但暴露方式不同，区别在于数据集规模：

| | 9-16（180 ep） | 9-18（223 ep） |
|---|---|---|
| 首个错配位置 | 落在视频文件边界附近 | 落在视频文件内部 |
| 表现 | **step 0 直接崩**：`Invalid frame index=10332 for streamIndex=0; must be less than 8832` | **完全无报错**，训练正常启动 |
| 暴露速度 | 立刻 | 不暴露（静默学错） |

9-16 那次之所以幸运，是错位后请求的帧号**越过了视频流的总帧数**，被解码器拦下；
9-18 错位后的帧号仍在视频长度范围内，于是安静地解码出一张**属于别的时刻**的图。

> 这就是为什么不能依赖「训练没报错」来判断数据是好的。

## 为什么不该在视频层修

视频侧是**完好的**，不需要也不应该动：

- 80 个 mp4 全部存在，0 缺失
- 每个视频的时长 ≥ meta 的 `to_timestamp`（余量精确 +0.00s）
- 223 集 × 3 相机逐一核对，无截断

损坏起源于**录制阶段崩溃残留的 writer 缓冲**（parquet 侧），视频文件本身没有半成品。
把 `tmp*/` 里那几个 ep161 录崩残留的 mp4 误解为「损坏的视频」，会修错对象。

## 为什么 `stats.json` 不用重算

`meta/stats.json` 各特征（`action` / `observation.state` / `timestamp` / `index` …）
的 `count` 都是 **533,168**，等于 meta 的 `total_frames`，而不是 parquet 实际行数 544,173。

说明统计量是**按逻辑视图（meta/episodes）聚合**的，废弃块从未参与计算
→ **未被污染，无需重算**。（相机特征 `count` 为 75,760，是解码后的像素级计数口径，同样自洽。）
