## 2. 决定性验证：证明「要删的就是哪一块」

不能靠"看起来像"就动手。做法是把**源端那个损坏文件下载到接收端**，用**同一个 pyarrow
版本**做逐单元格比对（跨机器比 sha256 会受版本影响，比内容才可靠）：

```python
src = pq.ParquetFile("/tmp/src_file009_corrupt.parquet")
a   = src.read_row_groups(list(range(10)))          # 只读前 10 个 row group
b   = pq.read_table(".../file-009.parquet")          # 接收端已验证良好的那份

a.num_rows == b.num_rows          → True   (23,823)
a.schema.equals(b.schema)         → True
a.equals(b)                       → True   ← 逐单元格完全相等
```

**结论**：丢掉最后一个 row group，得到的**就是**接收端那份已过 846 帧解码校验的文件，
一个单元格都不差。修复动作由此从"推测"变成"证明"。

## 8. ⚠️ 未确认的关键点：同步链路

侦察时**没能确认 b601 到底是怎么从 `192.168.60.183` 传到 `/data/share` 的**：

- 接收端跑着 Syncthing，但它共享的是 `~/Sync`，**不是** `/data/share`
- 源端**没有** Syncthing
- 两边 `~/.bash_history` 里都没有指向对方的 `rsync` / `scp` 记录

> ⚠️ 你的笔记里把机制写成了「rsync 判定需更新」「rsync 保留源端 mtime」。
> **结论仍成立**（Syncthing 同样保留 mtime，增量重传覆盖的行为一致），
> 但推理链条该改。建议确认后更新 [`02-损坏机理-物理行号等于index.md`](02-损坏机理-物理行号等于index.md)
> 与 [`05-预防与治本方案.md`](05-预防与治本方案.md) 里的措辞。

**为什么这件事重要**：如果链路中间还有别的机器或 staging 目录存着旧的 `file-009`，
那它**仍可能把损坏推回来**。本次只修了 `183` 上的那一份。

34,828 → 23,823 行这种不可逆的操作，靠的是证据链，不是「看起来对」。
