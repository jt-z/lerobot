# b601 数据集损坏与修复（精炼版）

> 详细版见同目录 [`00-项目元数据.md`](00-项目元数据.md) ~ [`05-预防与治本方案.md`](05-预防与治本方案.md)。

## 核心结论

**接收端修好的数据，会被源端下一次重传覆盖回损坏版**——因为损坏在源头就存在，
接收端的修复对源端不可见。所以在源端清理之前，**每次同步后都必须验一遍
`总行数 == meta total_frames`**，这一条判据就能捕获全部已知损坏。

## 关键知识点

- **`LeRobotDataset` 的硬约束：物理行号必须等于 `index` 值。**
  底层 HF datasets 按文件名顺序对 parquet 做**位置拼接**，而 episode 定位依赖
  `meta/episodes` 里的 `dataset_from_index`（一个全局行号）。两者一旦错位，
  `ds[i]` 就会取到别的 episode 的行。

- **损坏形态：末尾多一个 row group。**
  `file-009.parquet` 尾部的 11,005 行是 ep161 第一遍录制崩溃时泄漏的 writer 缓冲，
  全部标成 `episode_index=161`（真身只有 2,110 行，在 `file-010`）。
  它把其后所有内容整体后移 11,005 行 → **ep162 之后 ≈21% 的帧图文错配**。

- **同一损坏可以「崩」也可以「静默」，取决于数据集规模。**
  9-16（180 ep）时错位后的帧号越过了视频流总帧数 → 解码器拦下，step 0 就崩；
  9-18（223 ep）时错位后的帧号仍在视频长度内 → **完全无报错**，安静地学错。

- **视频侧是完好的，不要修错对象。**
  80 个 mp4 全部存在、0 截断，`to_timestamp` 余量精确 +0.00s。
  `tmp*/observation.images.*_161.mp4` 是录制崩溃的**视频侧**残骸，未入库。

- **`meta/stats.json` 未被污染。**
  其 `count` 为 533,168（== meta `total_frames`，而非 parquet 实际 544,173），
  说明统计量按**逻辑视图**聚合，废弃块从未参与计算 → 无需重算。

## 工作机制

```
源端录制 ep161 崩溃 → writer 缓冲残留进 file-009（源端从未修复）
                              │
                 每次重传（rsync）│ 接收端已修的 file-009 与源端不同 → 判定需更新
                              ▼
                接收端 file-009 被源端损坏版覆盖（sha256 逐字节相同）
                              │
                              ▼
        物理行号 ≠ index（file-010 起整体 +11,005）
                              │
                              ▼
   ds[i] 的 state/action 取错行；视频仍按 meta 的 episode+timestamp 查
                              │
                              ▼
                  图文错配，loss 正常，模型学错
```

## 重要决策与原因

| 决策点 | 选择 | 原因 |
|---|---|---|
| 修复粒度 | 按 **row group 边界**丢弃末块 | 无损、不重编码；9-16 已验证可行 |
| 重写时读法 | 只读**前 N−1** 个 row group | 废弃块不进内存，也不会再被写出 |
| 是否重算 stats | 不重算 | `count` 按逻辑视图算，未污染 |
| 是否修视频 | 不修 | 视频完好（0 缺失 / 0 截断），坏的是 parquet |
| 是否清 `tmp*/` | 暂不动 | 源端录制残留，不影响训练；归入治本选项 A |
| 修完怎么验 | 结构层 + 解码层两层 | 结构层秒级抓定位错误，解码层验证真实取帧与图文对齐 |

## 踩坑精华

| 问题 | 根因 | 解决的本质 |
|---|---|---|
| 9-18 损坏没被及时发现 | 训练不报错、loss 正常 | **不能靠「训练没崩」判断数据正常**，要有独立校验 |
| 首次去查「损坏的视频」 | 命名直觉误导：看到 `tmp*` 里有 `_161.mp4` | 先定位损坏**在哪一层**（数据 parquet vs 视频），再动手 |
| 用 mtime 判断文件有没有被覆盖 | rsync 保留源端 mtime | **mtime 不可信**，要用内容 sha256 / 行数比对 |
| 「episode 数对得上」以为没事 | 废弃块不改变集数，只改变**位置** | 要查 **`物理行号 == index`** 这个等式，而非集的计数 |
| 差值与预期不符时想「凑合修」 | — | 脚本设计成**只在差值 == 末尾 row group 行数时才动手**，否则拒绝执行 |

## 可复用的规律

1. **分块追加型数据集的「位置式寻址」是脆弱点。**
   只要元数据用「全局行号」定位、而存储用「文件顺序拼接」，任何一次异常写入
   （崩溃残留、中断续写、重复追加）都会造成**静默的全局错位**，
   且**越靠后的数据错得越一致——不会自愈、也不会报错**。
   通用体检项：`存储总行数 == 元数据总数` 且 `位置 == 逻辑序号`。

2. **「修复位置」要和「损坏来源」在同一侧，否则会被覆盖。**
   只修下游（接收端）而源端保持坏状态，修复就是一次性的，会在下次同步时被回滚。
   判断方法：比较损坏文件的 sha256 是否每次都完全相同——相同即说明「同一个坏文件被反复传下来」。

3. **静默损坏比崩溃更危险，而静默与否可能只是规模问题。**
   同一个 bug 在小数据集上崩、在大的上不崩（越界 vs 未越界）。
   **「以前会崩，现在不崩」不是修复的证据，可能只是越界条件不再满足。**

4. **判断损坏层级可以省掉一半工作量。**
   先明确「哪个 artifact 的哪条不变量被破坏」，再决定修什么。
   本次若按字面去修视频，会完全白费——视频没有任何问题。
