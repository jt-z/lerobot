# 05-预防与治本方案

## 为什么必然复现

废弃块不在接收端产生，它在**源端的录制阶段**就已经写进了 `file-009.parquet`：

```
ep161 第一遍录制 → 中途崩溃 → writer 缓冲残留在 parquet 末尾（11,005 行）
                 → 该集重录 → 真正的 2,110 帧写进 file-010
```

源端那份数据从 9-16 起就一直是坏的，**它在源头没有做过修复**
（9-16 和 9-18 两次修复都是在接收端 `/data/share/...` 做的）。

于是一个闭环：

```
源端每次重传 → 接收端已修的 file-009 与源端版本大小不同 → rsync 判定「需更新」
            → 用源端的损坏版覆盖 → 损坏复现
```

**9-18 的 sha256 与 9-16 记录的「原始损坏版」逐字节相同**，正是这一点的直接证据：
两次传下来的就是同一个文件。

> 附带一提：`tmpb_cyevai/`、`tmpui7cl1ya/`、`tmpwk91b9ul/` 里那三个
> `observation.images.{top,front,hand}_161.mp4` 是**同一次崩溃**留下的视频侧残骸。
> 它们没进数据集（视频是完好的），但足以佐证崩溃点在源端录制阶段。

## 治本选项

### 选项 A：在源端修（推荐，一次性）

在录制端的采集工程里，清掉那个崩溃会话残留的 writer 缓冲，让源端数据本身是干净的：

| 动作 | 说明 |
|---|---|
| 修源端的 `file-009.parquet` | 丢弃末尾 11,005 行 row group，方法同 [`03-file009-修复操作.md`](03-file009-修复操作.md) |
| 顺带清理 `tmp*` 残留 | 对应崩溃会话的临时编码目录 |
| 之后重传一次 | 接收端不用再修 |

**优点**：一劳永逸，此后任何一次同步、任何一台接收机拿到的都是干净的。
**缺点**：需要源端有写入权限和操作窗口。

### 选项 B：在接收端固化流程（保底）

把「修复 + 校验」变成同步后的固定动作：

```bash
# 每次从源端同步完之后
ROOT=/data/share/b601_20260910_164106

python .../datastet_notes/scripts/verify_dataset.py --root $ROOT   # 先看
# 若报「多出 11,005 行」：
python .../datastet_notes/scripts/fix_file009.py   --root $ROOT   # 再修
python .../datastet_notes/scripts/verify_dataset.py --root $ROOT   # 复验
# 全部通过才开训
```

**优点**：不依赖源端配合。
**缺点**：每次同步都得记得跑；漏跑就会静默学错（9-18 这次就是漏了）。

#### ✅ 已实现：自动化版本（2026-09-18）

上面那个「缺点」已经用钩子消掉了 —— 不用再记得跑：

```bash
cd self_scripts/stage3_train/dataset_b601_rs_makecoffee_train

bash bench/install_hook.sh status     # 看装了没 / 最近日志
bash bench/install_hook.sh install    # 装 cron（默认每 10 分钟轮询）
bash bench/install_hook.sh run        # 立即跑一次
bash bench/install_hook.sh uninstall  # 卸载
```

**当前状态：已安装**（`*/10 * * * *`，写在 crontab 里，带 `# b601-dataset-sync-check` 标记）。

设计要点：

| 机制 | 说明 |
|---|---|
| **三重守卫** | ① 单实例（flock）② 数据集静默 ≥5 分钟（传输未结束绝不动）③ 无 `lerobot-train` 在跑 |
| **指纹短路** | 数据集「路径+大小+mtime」哈希没变就直接退出 → 常态轮询几乎零成本 |
| **增量识别** | 日志里会记 `检测到增量：453139 180 → 533168 223` |
| **自动修复** | 检出即修（`--fix -y`），落盘前验证；日志留全过程 |
| **可调查** | 全部日志在 `bench/logs/post_sync.log`，超 2MB 自动截断 |

退出码：`0`=通过（含修复后通过）、`1`=需人工介入、`2`=被守卫跳过（正常）、`3`=环境错误。

> 为什么是**轮询**而不是事件触发：本机没装 `inotify-tools`，且增量重传没有固定的
> 「结束」事件。轮询 + 守卫让「跑得频繁」是安全的。

## 推荐

**A + B 一起做，但优先级不同**：

1. ~~**立即做 B**：把校验挂进流程~~
   **✅ 已完成**（见上面「已实现」小节）：`bench/install_hook.sh install` 已装，
   每 10 分钟轮询，检出即修并记日志。
2. **排期做 A**：源头修一次，之后 B 就只是例行体检，不会再报警。
3. **可选**：把 `bench/post_sync_check.sh` 加进 `start_train_act.sh` 的前置检查，
   让「数据是坏的」在开训前直接拦住（钩子有 10 分钟延迟，开训是更靠后的关卡）。

## 不建议的做法

| 做法 | 为什么不建议 |
|---|---|
| 靠「训练没报错」判断数据正常 | 9-18 全程无报错，但 21% 的帧图文错配 |
| 靠文件 mtime 判断有没有被重传覆盖 | rsync 保留源端 mtime，覆盖后时间戳不变 |
| 只在视频层排查 | 视频完好；损坏在数据 parquet 层，查错对象会白费功夫 |
| 每次重传后手工重做一遍 | 9-16 和 9-18 两次都是手工做的，第二次隔了两天才发现 |
| 修复前先重算 `stats.json` | 不必。`count` 是 533,168（按 meta 逻辑视图算的），未被废弃块污染 |

## 长期观察点

- **源端还会不会有新的崩溃残留**：本次残留来自「录制中途崩溃」这一特定事件。
  若之后又出现类似的崩溃-重录，可能在**别的文件**里留下同类块。
  校验脚本不假设「多余的块一定在 file-009」，它是按「总行数差值 == 末尾 row group 行数」判断的，
  但仍建议发现新模式时人工确认后再修。
- **增量传输的批次规律**（9-16 不规则、9-17 零新增、9-18 两批间隔 28 分钟）
  说明源端是**随手推**的。若之后要改成自动同步，更要保证 B 的校验在同步后自动触发。
