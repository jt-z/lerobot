# pi05 时延与显存分析

目的：记录 pi05 在 RTX 3060 12GB 上的显存占用、分段时延、实时性预算，以及实测出的优化边界。
数据来源：`lx/PI05_HANDOFF.md`、`lx/PI05_LATENCY.md`（2026-11-11 锁定态 / 2026-11-12 算力解锁态）。

## 一、测试条件

| 项 | 值 |
|---|---|
| GPU | RTX 3060 12GB（GA106） |
| 模型 | `lx/output_pi05/007000/pretrained_model`（pi05，全量微调 7k 步） |
| 配置 | token 96 / 视觉塔 bf16 / 10 步去噪 / chunk 50 / 30Hz / 三路 480×640 MJPG |
| 机器人 | 单 B601-RS 从臂（can0，1Mbps） |
| 解锁 | `nv-uefi-unlocker` 易失性解锁（SM 1777~1905MHz，功耗上限仍 170W） |

## 二、显存

| 步骤 | 显存 | 性质 |
|---|---|---|
| fp32 权重（磁盘/理论） | 16.57GB | 4.143B × 4B |
| ① 按 bf16 构建 | 8.28GB | 等于训练精度 `dtype=bfloat16` |
| ② 跳过 2 个 lm_head | −1.58GB | 纯删除（790M 参数） |
| ③ 跳过 expert 词嵌入 | 构建期 −0.53GB | 纯删除（263M，checkpoint 里没有） |
| ④ 视觉塔 fp32（原版行为） | +0.82GB | 412M 参数 |
| ⑤ 视觉塔 bf16（默认） | −0.82GB | — |
| **实测最终** | **6.97GB**（视觉 bf16）/ **7.78GB**（视觉 fp32） | 峰值 7.78 / 7.95GB |

没有量化、剪层、降分辨率、减相机；②③ 删的是推理路径上不存在的计算。

## 三、单 chunk 时延（真机）

| 条件 | mean | p50 | p95 | p99 | 停顿 |
|---|---|---|---|---|---|
| 锁定 · sync | 437.0ms | — | 450 | 452 | 每 1.667s 停 437ms |
| **解锁 · sync** | **353.9ms** | 353 | 364 | 377 | 每 1.667s 停 354ms |
| 锁定 · rtc | 558.9ms | — | 588 | 598 | 无 |
| **解锁 · rtc** | **501.3ms** | 499 | 524 | 541 | 无 |

- 算力解锁对 sync 的实际收益 **1.24×**（437 → 354），不是标称 1.83×
- rtc 比 sync 多 147ms，几乎全来自宿主侧争用（后台推理线程 vs 30Hz 主循环 / MJPG 解码 / CAN）
- 两次解锁态 sync 相差 1ms，可复现性很好

## 四、分段归因（解锁态）

| 阶段 | 锁定 sync | 解锁 sync | 解锁 rtc | 解锁/锁定 |
|---|---|---|---|---|
| embed（3×SigLIP + 文本） | 49.2ms | 38.1ms | 41.2ms | 1.29× |
| prefix_fwd（2.5B 主干） | 183.5ms | 116.4ms | 157.6ms | **1.58×** |
| denoise（10 步） | 204.3ms | 199.3ms | 302.4ms | **1.03×** |
| **total** | **437.0ms** | **353.9ms** | **501.3ms** | 1.24× |

结论：

1. **prefix 是唯一接近 compute-bound 的段**，已接近解锁增益上限；想再快只能减 token。
2. **denoise 基本不吃算力**：受 kernel launch、4D mask 重建、每步 `clone_past_key_values` 限制。解锁前占 46.7%，解锁后占 **56.3%**。
3. embed 只 1.29×：三路 480×640→224 resize + 归一化在 CPU 侧。
4. rtc 的额外开销（denoise +103ms、prefix +41ms）是宿主争用，加 GPU 算力压不掉。

## 五、实时性预算

chunk 覆盖 50 步 / 30Hz = **1667ms**。

| | 锁定 sync | 解锁 sync | 解锁 rtc |
|---|---|---|---|
| 单段占预算 | 26.2% | 21.2% | 30.1% |
| 停顿 | 437ms（13 tick） | 354ms（11 tick） | 0 |
| 预取触发点 | — | — | 剩 35 步（1167ms） |
| 推理后剩余 | — | — | 约 20 步（666ms） |
| 断流阈值 | — | — | chunk 时延 > 约 1.16s |

rtc 余量约为当前时延的 2.3 倍，正常负载不会断流；实测 rtc 日志 `real_delay` p50=16、min=14，队列 `indexes_diff=14~17`。

## 六、离线 bench 对照

`--chunks 12 --tokens 96`（随机图像 + 随机 token，不需要机器人）：

| 条件 | total | embed | prefix_fwd | denoise |
|---|---|---|---|---|
| 锁定 | 443ms | 47 | 173 | 219 |
| 解锁 | 381.2ms（p95 383） | 39 | 123.2 | 218.9 |

bench 的 denoise 比真机高约 20ms，其余一致；**绝对值以真机为准**。

```bash
. self_scripts/b601_common/_env.sh
LITE_VISION_BF16=1 python lx/tools/pi05_lite.py --bench 007000 --chunks 12 --tokens 96
```

⚠️ bench 注意：

1. 不传 `--tokens` 时会读 `config.tokenizer_max_length`（**200**），而真机预处理是 **96**，数值会明显偏慢。
2. `--bench` 会安装分段计时包装器；`LITE_TRACE=1`（默认）时每 chunk 约 21 次 `cuda.synchronize()`，会串行化 CPU 发射与 GPU 执行。测真实吞吐应 `LITE_TRACE=0`。

## 七、优化边界与建议

1. **继续加算力收益有限**：解锁端到端只 1.24×，denoise/embed 的 CPU 侧部分不受益。
2. **下一步只值得压 denoise**（占 sync 56%、rtc 60%）：`compile_mode=default` 或 CUDA graph，目标是 kernel 启动、mask/KV 重建，而不是算力。
3. **停顿观感改善有限**：437 → 354ms 只差约 1.5 tick；要彻底消除停顿只能用 rtc。
4. 解锁后 rtc 余量从 18 步升到 20 步，可把 `queue_threshold` 从 35 降到 30，把视觉滞后从 1.17s 缩到 1.0s（代价是余量降到 15 步）。
5. 若换 4090 级显卡，sync 停顿可压到 150~220ms，届时优先用 sync（输出最接近训练分布）。
6. **解锁是易失的**：重启/断电恢复锁定态，每次开机需重放：

```bash
sudo python3 lx/nv-uefi-unlocker/tools/diag-unlock.py --bdf 0000:01:00.0 | grep -E "PLM|SS0|READOUT"
```
