## 二、详细说明

### R1 · 相机检查只告警不退出

**现象**：`b601_check_cameras` 对不存在的 `/dev/v4l/by-id/...` 只打印 `❌ 警告：摄像头不存在`，没有 `exit 1`。

**后果**：pi05 的 `_preprocess_images` 对缺失相机用**全 -1 空图 + mask=0** 补齐（`modeling_pi05.py:1238-1244`），模型可以在“少一路视角”的情况下继续输出动作。`robot.connect()` 通常会先报错兜住，但相机存在却返回黑帧/错帧时没有任何保护。

**建议**：在推理脚本里对三路相机硬失败，与 ACT 的 `run_act_place_area.sh:89-98` 保持一致：

```bash
for cam in "${B601_CAMERA_DEVS[@]}"; do
  [ -e "$cam" ] || { echo "❌ 相机不存在：$cam"; exit 1; }
done
```

### R2 · ACTION_TRACE 与 ENTRY_WRAPPER 冲突

**现象**：`b601_run_rollout` 的选择顺序是 `ENTRY_WRAPPER` → `ACT_VIZ` → `ACTION_TRACE` → `lerobot-rollout`（`_common.sh:253-266`）。pi05 默认 `LITE_LOAD=1`，所以即使用户显式 `ACTION_TRACE=1`，也走 lite 包装器，动作追踪不会生效。

**后果**：参数总览仍打印“动作追踪：✅ sent/cmd 逐 tick 记录到 action_test.log”（`pi05_inference.sh:160` 调 `b601_print_trace_summary`），实际没有日志文件，排障时会被误导。

**建议**：二选一——
1. lite 包装器内部串联 `action_trace` 的钩子；
2. 启动时检测 `ACTION_TRACE=1 && LITE_LOAD=1` 直接报错，提示改用 `LITE_LOAD=0` 或关追踪。

### R3 · bench 默认值与测法

**现象**：
- `token_len = token_len or policy.config.tokenizer_max_length`（`pi05_lite.py:361`），而 `config.json` 是 200；真实预处理器被改成了 96。
- `main()` 在 `--bench` 时无条件 `_install_timing()`（`:399`）；`LITE_TRACE=1` 时 `embed_prefix`/`denoise_step` 每次调用前后都 `cuda.synchronize()`，10 步去噪即 ~21 次同步。
- `_bench` 里“只在循环首尾同步”的注释（`:379`）与上述行为矛盾。

**后果**：脚本头部给出的 bench 命令（`pi05_inference.sh:28`）会得到偏慢且与真机不同 token 长度的数值，不能直接和 354ms 的真机数据对比。

**建议**：bench 默认 `token_len` 从预处理器读 `max_length`（或脚本默认传 `--tokens 96`）；测吞吐时 `LITE_TRACE=0`，需要分段数据再单独跑。

### R4 · lite 路径缺 `eval()` / `to(device)`

**现象**：原生 `PreTrainedPolicy.from_pretrained` 末尾会 `policy.to(config.device)` + `policy.eval()`（`pretrained.py:203-204`）；lite 的 patched 版本只依赖构造期的 `torch.device(device)` 上下文，没有显式这两步。

**后果**：当前模型无 dropout，参数也在正确设备上，所以没有实际故障；但属于与原生路径的隐性行为差异，后续加 dropout 或改设备参数时会踩坑。

**建议**：patched 末尾补 `policy.to(device)` 和 `policy.eval()`。

### R5 · 用法示例指向 `003000`

**现象**：`pi05_inference.sh:16` 示例 `bash lx/pi05_inference.sh 003000`，但 `lx/output_pi05/` 下只有 `007000`；`lx/PI05_HANDOFF.md` 明确 `003000` 是截断文件（safetensors 头声明 16.57GB，实际 11.2GB）。

**建议**：示例改成 `007000`，或直接删除该行。

### R6 · `LITE_VISION_BF16` 默认值不一致

`pi05_lite.py:28` 的 docstring 写默认 0（“需先用 verify_actions 做精度回归”），而 `pi05_inference.sh:73` 默认导出 1，且精度已验证（0.249°，门槛 1°）。以脚本为准，建议更新 docstring。

2026-11-11 复核：包装器 `pi05_lite.py:278` 仍写 `os.environ.get("LITE_VISION_BF16", "0")`，但脚本每次都会 `export`，实际生效 bf16（日志有 `[pi05-lite] 视觉塔改用 bf16`）。仅剩文档/默认值不一致，降级为纯文档问题。

### R7 · TASK_INDEX 非数字输入

`if [ -z "${TASKS[$TASK_INDEX]:-}" ]` 中下标参与 bash 算术求值：`TASK_INDEX=abc` 会被当成变量名求值为 0，最终静默使用第 0 条任务。

**建议**：先校验 `[[ "$TASK_INDEX" =~ ^[0-9]+$ ]]` 再做范围判断。

### R8 · `_drop_lm_head` 的参数统计

`lm_head` 在构建期已被建成 `out_features=0`，`head.weight.numel()` 为 0，所以日志打印“摘下 lm_head：0M 参数”。真实省下的量在 `skipped_heads` 里（262144）。建议用 `skipped_heads` 统计，或把日志措辞改成“摘除占位 head”。

### R9 · 加载期 2.1GB 主机内存尖峰

`_fix_pytorch_state_dict_keys` 会把 paligemma 的 lm_head `clone()` 到 `embed_tokens` key（`modeling_pi05.py:1114`）：262144×2048 fp32 ≈ 2.1GB，是 mmap 之外的匿名内存。kfzbox 可用内存约 8.7GB，正常情况下能过，但和别的进程并发时会紧张。

**可选优化**：若确认 checkpoint 里 embed_tokens 与 lm_head 同值（tied），可跳过 clone，直接复用原 key。

### R10 · `TASK_DESCRIPTION` 被 `_common.sh` 覆盖（P0，已修）

**现象**：`_common.sh` 在 source 时无条件给 `TASK_DESCRIPTION` 赋了另一套旧任务（“Pick up the paper cup, place it on the silver tray of the coffee machine, pick up the cube, press the button with the cube (red light on), wait about 4 seconds, …”），而脚本写的是 `${TASK_DESCRIPTION:-${TASKS[$TASK_INDEX]}}`——变量已被赋值，默认值永远取不到。

**后果**：2026-11-11 前两次真机运行（sync 与 rtc）传给模型的都是这条**不在 b601_mixed 4 条任务里的 OOD 指令**，首段出现大幅异常动作。任务 0 最终仍能完成，属运气。

**修复**：source 之前先快照用户显式传入的值：

```bash
_B601_TASK_DESC_ENV="${TASK_DESCRIPTION:-}"
...
TASK_DESCRIPTION="${_B601_TASK_DESC_ENV:-${TASKS[$TASK_INDEX]}}"
```

**验证**：启动总览的「任务文本（b601_mixed 第 N 条）」应随 `TASK_INDEX` 变化。

### R11 · `INFERENCE_TYPE` 默认 `rtc` 永不生效（P1，已修）

**现象**：`_common.sh` source 时把 `INFERENCE_TYPE` 置为 `sync`（其它策略的默认值），脚本的 `${INFERENCE_TYPE:-rtc}` 因此取不到默认。

**后果**：默认实际跑 sync（每 1.667s 停约 354ms），且 `RTC_ARGS` 整个为空；日志里是 `Creating inference engine: sync`。同一机制还让 `ACTION_TRACE` 被置 1（见 R2）。

**修复**：与 R10 同一手法，source 前快照 `INFERENCE_TYPE` / `ACTION_TRACE`，之后再用 `${_B601_*_ENV:-默认值}` 解析。

**验证**：总览显示「推理后端：rtc」和「RTC 参数：queue_threshold=35 / execution_horizon=20」。

### R12 · 启动前缺 can0 复位（P1，已修）

`02_record.sh` 一直在连接前 `down → 1Mbps → up` 并读空残留帧，推理脚本只判断接口 `UP` 就直接连接。上次异常退出后控制器可能停在半状态，`disable_all` 等不到 ACK，报 `control ack timeout: comm_type=4`。

已补上与采集脚本一致的复位逻辑；细节与排查顺序见 [问题_推理启动CAN应答超时](../02_数据采集/问题_推理启动CAN应答超时.md)。

## 三、建议修复顺序

1. ~~R10~~（P0，已修：错误的 prompt 会让动作直接失效）
2. R1（真机安全边界，改动最小）
3. R2 / R11 / R12（排障可信度与启动可靠性，R11/R12 已修）
4. R3（测速可信度）
5. R4 + R8 + R5/R6/R7（行为一致性与文档）
6. R9（仅在内存紧张时处理）

> 共同教训：`_common.sh` 会**无条件覆盖**多个环境变量（`INFERENCE_TYPE` / `ACTION_TRACE` / `TASK_DESCRIPTION` 等）。任何「在 source 之后写 `${VAR:-默认值}`」的默认值都不生效，必须先在 source 前快照用户输入。新增变量时按同一模式处理。
