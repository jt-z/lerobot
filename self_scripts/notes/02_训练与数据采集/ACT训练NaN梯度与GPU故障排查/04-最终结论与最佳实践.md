# 最终结论与最佳实践

## 核心结论

**一句话总结**：ACT训练中的NaN梯度源于VAE配置过激进（kl_weight=10.0），降至1.0并减小批次、学习率后稳定；GPU 0硬件失效后改用7卡继续训练。

---

## 问题与方案总结

### 问题1：NaN梯度导致CUDA崩溃

| 维度 | 内容 |
|------|------|
| **直接原因** | VAE KL散度计算中 `exp(log_sigma_x2_hat)` 数值溢出 |
| **深层原因** | kl_weight=10.0过高 + 4层VAE编码器 + 大批次(256) |
| **核心解决方案** | kl_weight降至1.0 |
| **辅助措施** | 批次16、学习率5e-5、2层编码器、梯度裁剪5.0 |
| **效果** | 参数从52M降至43M，训练稳定 |

### 问题2：GPU 0硬件失效

| 维度 | 内容 |
|------|------|
| **表现** | nvidia-smi无法识别GPU 0，PyTorch退回CPU |
| **可能原因** | CUDA崩溃后驱动状态异常 或 硬件故障 |
| **立即方案** | 使用CUDA_VISIBLE_DEVICES=1,2,3,4,5,6,7绕过 |
| **影响** | 有效批次128→112，训练时间+13% |
| **长期方案** | 重启服务器 或 硬件检查 |

## 可复用的规律

### 1. VAE训练的数值稳定性原则

**核心**：KL散度的权重要保守，特别是训练初期

**经验值**：
```
推荐范围：kl_weight ∈ [0.1, 2.0]
起始值：1.0
最大值：不超过 5.0
```

**为什么**：
- KL散度的exp项是无界的
- 过高的权重会让网络"冒险"调整方差
- 导致 log_sigma 进入危险区域

### 2. 批次大小的选择

**权衡**：
```
大批次 → 梯度估计准确 + 计算效率高 - 数值不稳定风险高
小批次 → 训练稳定 + 正则化效果 - 收敛可能变慢
```

**推荐策略**：
- 训练初期：使用中小批次（16-32）建立稳定基线
- 训练稳定后：可以逐步增大批次提高效率
- 多GPU：每卡16是经验甜点（有效批次=16×GPU数）

### 3. 梯度裁剪的作用

**不是万能药，但是必要的保护**：
- 无法解决根本的数值问题（NaN已产生时裁剪无效）
- 但能防止偶发的梯度尖峰破坏训练
- 配合其他措施形成多层保护

**推荐值**：
```
保守：5.0（本次使用）
中等：10.0（常见默认值）
激进：20.0+（仅用于已知稳定的模型）
```

### 4. 分布式训练的GPU故障应对

**设计原则**：允许GPU数量变化
```bash
# 好的做法：环境变量控制
CUDA_VISIBLE_DEVICES=1,2,3 accelerate launch --num_processes=3 ...

# 不好的做法：硬编码GPU数量
accelerate launch --num_processes=8 ...  # GPU数量变化时失败
```

**效果**：
- 部分GPU失效时可以继续训练
- 调试时可以只用部分GPU
- 灵活适应不同硬件环境

### 5. 调试模式的性能代价

**CUDA_LAUNCH_BLOCKING=1的双刃剑**：
- ✓ 精确定位错误位置
- ✗ 让训练速度降低10-100倍

**使用策略**：
```
正常训练：不开启
出现崩溃：开启一次，定位错误后立即关闭
持续调试：只在单GPU小数据上开启
```

### 关键经验

**1. 不要盲目相信默认配置**
- 默认的 `kl_weight=10.0` 对很多任务过于激进
- 根据数据集规模和任务复杂度调整

**2. 训练前验证数据**
- 数据问题会导致无法解释的训练失败
- 10分钟的验证能省数小时的排查时间

**3. 增量式调试**
- 从最保守配置开始
- 确认稳定后再逐步优化
- 每次只改一个参数

**4. 保留应急方案**
- 准备多个配置文件（稳定版、无VAE版）
- 准备GPU故障应对脚本
- 定期保存checkpoint
